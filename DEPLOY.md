# Deploying MedScan AI — frontend on Netlify, backend on Render

The frontend is a static Vite bundle (`client/dist`); the backend is one FastAPI process
(built from `server/Dockerfile`) plus PostgreSQL. Three files drive the deploy:

| File | Read by | What it sets |
|---|---|---|
| `netlify.toml` (repo root) | Netlify | Build settings, the `/api/*` proxy rule, the SPA fallback |
| `render.yaml` (repo root) | Render (Blueprint) | The API service + its Postgres, with every env var |
| `server/Dockerfile` | Render | Python 3.12 image, `uvicorn ... --port 8000` |

## How traffic flows once deployed

```
browser ── page + JS/CSS ─────────────────────────────▶ Netlify (static client/dist)
browser ── API calls (absolute VITE_API_URL) ─────────▶ Render web service :8000 ──▶ Render Postgres
browser ── <img src="/api/v1/uploads/file/…?token=…"> ─▶ Netlify /api/* proxy ──▶ Render ──▶ Cloudinary
```

The third line exists because the API returns study files as **relative** signed URLs
(`server/app/storage/local.py`, `cloudinary.py`, `fallback.py`) and the UI puts them
straight into `<img>`/`<video>` tags, so the browser requests them from the Netlify origin.
`netlify.toml` proxies `/api/*` to Render — the same thing `client/nginx.conf` does for
docker-compose. Only those file fetches use the proxy: Netlify proxies time out after 26 s
and an AI analysis can run longer, so the app's own API calls go straight to Render.

## 0. Push to GitHub

Both platforms deploy from the GitHub repo, not from your disk.

```bash
git add -A
git commit -m "Deployment config for Netlify + Render"
git push origin main
```

`server/.env` and `client/.env` are gitignored and stay local. Secrets go into each
platform's environment-variable UI instead.

## 1. Render — backend + database

### Option A — Blueprint (recommended: one screen, nothing to mistype)

1. Render Dashboard → **New → Blueprint** → connect the GitHub repo.
2. Render reads `render.yaml` and shows the two resources it will create: `medscan-db`
   (Postgres 16) and `medscan-api` (Docker, root directory `server`, health check
   `/api/v1/health`, port 8000).
3. It prompts for every `sync: false` value:

   | Prompt | What to enter |
   |---|---|
   | `CLIENT_URL` | Your Netlify URL if you already know it, otherwise `https://placeholder.netlify.app` — you fix it in step 3 |
   | `GEMINI_API_KEY` | From https://aistudio.google.com |
   | `CLOUDINARY_CLOUD_NAME` / `CLOUDINARY_API_KEY` / `CLOUDINARY_API_SECRET` | Cloudinary Console → Dashboard |

   `JWT_SECRET` and `SIGNED_URL_SECRET` are generated by Render; `DATABASE_URL` is wired
   from the database automatically.
4. **Apply.** First build takes a few minutes. Copy the service URL Render shows
   (`https://medscan-api.onrender.com` or with a suffix if the name was taken) — you need
   it in three places in step 2.

### Option B — manual, in the dashboard

1. **New → PostgreSQL**: name `medscan-db`, Postgres 16, pick a region. After it's created
   copy the **Internal Database URL** (starts with `postgresql://`; the app rewrites the
   scheme to `postgresql+asyncpg://` itself — `server/app/core/config.py`). Do not use the
   External URL: it needs SSL parameters the internal one doesn't.
2. **New → Web Service** → the GitHub repo → **Language: Docker** → **Root Directory:
   `server`** → same region as the database → **Health Check Path: `/api/v1/health`**.
3. **Environment** tab → add every row of the table below → **Create Web Service**.

### Environment variables — complete list

Variable names are exact (they are the `alias=` values in `server/app/core/config.py`).

**Required — the app refuses to start without these**

| Key | Value |
|---|---|
| `DATABASE_URL` | The Internal Database URL from Render (`postgresql://…`) |
| `JWT_SECRET` | Long random string: `python3 -c "import secrets; print(secrets.token_urlsafe(64))"` |
| `SIGNED_URL_SECRET` | Another long random string, different from `JWT_SECRET` |

**Deployment / proxy — needed for this hosting setup to behave**

| Key | Value | Why |
|---|---|---|
| `ENVIRONMENT` | `production` | HSTS header on, INFO-level logs |
| `PORT` | `8000` | What the Dockerfile's `uvicorn` command binds; tells Render where to route |
| `FORWARDED_ALLOW_IPS` | `*` | Read by uvicorn, not the app: trust `X-Forwarded-For` from Render's proxy so the per-IP rate limiter sees real users. Without it all users share one bucket — 30 logins per 15 min in total |
| `CLIENT_URL` | `https://<your-site>.netlify.app` | The only CORS-allowed origin, and the base for password-reset and Stripe return links. Exact browser origin: `https`, no trailing slash, no path |

**AI — pick one provider**

| Key | Value |
|---|---|
| `AI_PROVIDER` | `gemini` (default) — or `anthropic`, or `mock` for zero-cost placeholder output |
| `GEMINI_API_KEY` | Required when `AI_PROVIDER=gemini` |
| `AI_API_KEY` | Required when `AI_PROVIDER=anthropic` |
| `GEMINI_MODEL`, `GEMINI_IMAGING_MODEL`, `GEMINI_SUMMARY_MODEL`, `GEMINI_HIGH_ACCURACY_MODEL`, `GEMINI_FALLBACK_MODELS` | Optional overrides; defaults documented in `server/.env.example` |

**File storage — Render's disk is wiped on every deploy and restart, so never `local`**

| Key | Value |
|---|---|
| `STORAGE_PROVIDER` | `cloudinary` |
| `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET` | From Cloudinary Console → Dashboard (or the single `CLOUDINARY_URL` instead of the three) |
| `STORAGE_FALLBACK_PROVIDER` | Optional, e.g. `firebase`: uploads land there when Cloudinary is down |
| `FIREBASE_CREDENTIALS_PATH` | Only with the Firebase fallback: Render → service → **Secret Files** → upload the service-account JSON as `firebase.json`, then set this to `/etc/secrets/firebase.json` |
| `FIREBASE_STORAGE_BUCKET` | Only with the Firebase fallback |
| `STORAGE_BUCKET`, `STORAGE_REGION`, `STORAGE_ACCESS_KEY`, `STORAGE_SECRET_KEY`, `STORAGE_ENDPOINT_URL` | Only for `s3` / `s3_compatible` |
| `MAX_UPLOAD_MB` | Optional, default 50 |

**Sign in with Google — optional (email/password login works without it)**

| Key | Value |
|---|---|
| `GOOGLE_CLIENT_ID` | The OAuth client id; the same value goes into Netlify as `VITE_GOOGLE_CLIENT_ID` |

**Billing — optional; the free trial works with these blank**

| Key | Value |
|---|---|
| `STRIPE_SECRET_KEY` | Stripe Dashboard → Developers → API keys |
| `STRIPE_PRICE_ID` | The recurring price to sell (Products) |
| `STRIPE_WEBHOOK_SECRET` | Signing secret of the webhook endpoint you create in step 3 |
| `TRIAL_DAYS`, `TRIAL_DAILY_REPORT_LIMIT` | Optional, defaults 3 and 100 |

**Tuning — optional, defaults are fine**

`JWT_ACCESS_TOKEN_MINUTES` (30), `JWT_REFRESH_TOKEN_DAYS` (30), `SIGNED_URL_TTL_SECONDS`
(300), `RATE_LIMIT_AUTH_PER_15MIN` (30), `RATE_LIMIT_API_PER_15MIN` (600).

### Check the backend before touching Netlify

- `https://<api>.onrender.com/api/v1/health` →
  `{"success":true,"data":{"status":"ok","aiConfigured":true}}`. `aiConfigured: false`
  means the AI key is missing.
- `https://<api>.onrender.com/docs` shows the Swagger UI.
- Render → Logs shows `Application startup complete (environment=production)`. The first
  boot also creates every table.

## 2. Netlify — frontend

1. **Put the Render host into `netlify.toml`**: replace `REPLACE-WITH-YOUR-RENDER-SERVICE`
   in the `/api/*` redirect with your real host (e.g. `medscan-api.onrender.com`). Commit
   and push — Netlify deploys from Git, so an uncommitted edit does nothing.
2. Netlify → **Add new site → Import an existing project** → GitHub → the repo. Netlify
   reads `netlify.toml`; the fields should already show **Base directory `client`**, **Build
   command `npm run build`**, **Publish directory `client/dist`**. Leave them.
3. Before the first deploy, open **Site configuration → Environment variables** and add:

   | Key | Value |
   |---|---|
   | `VITE_API_URL` | `https://<api>.onrender.com/api/v1` — the same host as in `netlify.toml`, with `/api/v1` |
   | `VITE_GOOGLE_CLIENT_ID` | Optional; the same client id as Render's `GOOGLE_CLIENT_ID` |

   Never set `VITE_SKIP_AUTH` here — it disables the login redirect and is dev-only.
   `VITE_*` values are baked into the JavaScript at build time: after changing one, use
   **Deploys → Trigger deploy → Clear cache and deploy site**.
4. **Deploy site.** Optionally rename it first (**Site configuration → Site details →
   Change site name**) so the URL you put into Render's `CLIENT_URL` stays stable.

## 3. Wire the two together

- **Render → `medscan-api` → Environment → `CLIENT_URL`** = the Netlify URL, e.g.
  `https://medscan.netlify.app`. Exact origin, no trailing slash. Saving redeploys.
- **Google sign-in** (if used): Google Cloud Console → APIs & Services → Credentials → your
  OAuth client → **Authorized JavaScript origins** → add the Netlify URL.
- **Stripe** (if used): Developers → Webhooks → **Add endpoint** →
  `https://<api>.onrender.com/api/v1/billing/webhook`, events `checkout.session.completed`,
  `customer.subscription.updated`, `customer.subscription.deleted`. Copy its signing secret
  into Render as `STRIPE_WEBHOOK_SECRET`.

## 4. Verify

- [ ] Health URL returns `"status":"ok"` and `"aiConfigured":true`.
- [ ] Sign up and log in on the Netlify site. A CORS error in the browser console means
      `CLIENT_URL` on Render doesn't match the Netlify origin exactly.
- [ ] Create a patient and study, upload an image, and confirm the preview renders. A
      broken image means the `/api/*` rule in `netlify.toml` still points at the wrong host.
- [ ] Run an analysis and open the report; download the PDF.
- [ ] Refresh the browser on a deep link such as `/reports/<id>` — it must not 404.
- [ ] Render → Logs show different client IPs for different users (proves
      `FORWARDED_ALLOW_IPS`).
- [ ] Google sign-in, if configured.

## Known limits of this setup

- **Free tiers.** A free Render web service sleeps after 15 idle minutes and takes about a
  minute to wake, so the first request after a pause is slow (the frontend waits up to
  120 s). A free Render Postgres holds 1 GB and is **deleted 30 days after creation** (14-day
  grace period after the warning email). Use paid instances for anything holding real
  patient data.
- **Netlify deploy previews and branch deploys** live on other origins, so the backend's
  single-origin CORS blocks them. Only the production URL in `CLIENT_URL` works.
- **One API instance only.** The rate limiter is in-process (`server/app/middleware/
  rate_limit.py`); scaling Render to several instances needs the Redis-backed limiter the
  README lists as future work.
- **AI analysis runs synchronously inside the HTTP request** (no background worker). If a
  long analysis fails with a gateway error rather than an application error, Render's proxy
  timed the request out — that is the "background job queue" item in the README.
- **No email delivery.** Password-reset links and invite passwords are only logged; read
  them from Render → Logs.
- **Schema changes.** Tables are created and new columns added at startup
  (`server/app/database/schema_sync.py`); anything beyond adding a column still needs a
  real migration before deploying.
